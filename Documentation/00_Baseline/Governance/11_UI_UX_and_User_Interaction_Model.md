# 1. First Run Experience and Risk Acknowledgment (初回起動時の重要リスク確認ゲート)

GST は、Windows ファイアウォール、レジストリ（WER等）、およびファイルシステムに関与する「個人開発（AI支援）による実験的ソフトウェア」である。初回起動時には、利用者が実験的性質、想定されるリスク、重要データの保護方針を確認できる**個別チェック必須のリスク確認ダイアログ（`FirstLaunchRiskAcknowledgmentDialog`）**を提示する。本ダイアログは法的な利用規約や権利放棄への同意を取得するためのものではない。

## 1.1 初回セットアップ ＆ 重要リスク確認ダイアログ (`FirstLaunchRiskAcknowledgmentDialog`)
すべての確認項目にチェックを入れない限り、`[ 内容を確認して始める ]` ボタンは有効化されない（Disabled 状態を維持する）。

# 2. UI Philosophy

## 2.1 Core Principle
GSTでは、高機能であることより、**ユーザーが理解し、取り返しのつかないミスを防げること** を優先する。
```
Explain Before Execute
Show Before Change
Confirm Before Risk
```

## 2.2 Transparency Requirement
すべての重要操作では、以下を説明する。
```
What Will Happen / Why It Is Needed / What Will Change / How To Recover
```

# 3. Progressive Disclosure and Settings UX (設定の段階的開示)

## 3.1 Normal Mode と Expert Mode の厳格な分離
* **Normal Mode (初期状態):** ゲーム登録、ゲーム起動、保護状態、バックアップ履歴、問題発生時の復旧、および「推奨設定」を中心とした日常導線を表示する。
* **Advanced / Expert Mode:** 「高度な設定を表示」を選択したユーザーに、個別Firewall rule CRUD、Global Override、KDFパラメータ、詳細監査、Migration、Archive等の専門操作を段階的に露出させる。MOD、Smart IME、Anti-Wiper等は高度機能という理由だけで一律に隠さず、頻度・対象ユーザー・失敗時影響・目的明確性で配置する。

### 3.1.1 Firewall遮断時の標準ユーザー導線
Firewallによる遮断が発生した場合、ユーザーは少なくとも **対象ゲーム / 対象実行ファイル / 通信方向 / 適用ポリシーまたはルール / 想定される影響 / 現在利用可能な次の操作** を確認できるようにする。一般ユーザーへ個別rule CRUDを要求せず、設定変更や例外変更は `Review → Confirm → Execute` を通す。

「今回のみ」「この実行ファイルのみ」などの未定義スコープをUIへ先行表示してはならない。変更後はWindows Firewall実状態を確認し、失敗・部分適用時は既存のReconcile結果をユーザーへ提示する。

## 3.2 目的ベースのUI (Task-Oriented UI)
システム主導の表現ではなく、ユーザーの目的をベースに配置する（例: 「🚫 このゲームの裏側での外部通信を遮断する」）。

## 3.3 セーフデフォルト ＆ お守りボタン (Standard Profile Reset)
設定画面の最上部には常に **「🛡️ 標準の推奨設定（Standard Profile）に戻す」** ボタンを配置し、一瞬で安全な初期状態に巻き戻せるようにする。

## 3.4 保護状態と設定状態の分離
ユーザー向け表示では、**保護状態**と**設定状態**を別の情報として扱う。設定をカスタマイズしたこと自体を「保護の異常」と解釈してはならない。

### 保護状態
- 🟢 **保護中** — 現在有効とされる保護経路が正常に動作している。
- 🟡 **一部制限あり** — 本来利用対象となる保護経路の一部に実行上の制限・障害があるが、残る保護経路は継続して動作している。
- 🔴 **保護停止** — 対象となる保護経路が停止し、当該保護を継続できない。

### 設定状態
- **標準設定** — Standard Profileに従っている。
- **カスタム設定** — ユーザーが標準設定から一つ以上の設定を変更している。

**重要:** 「カスタム設定」は保護異常を意味しない。ユーザーが任意のオプション機能を意図的にOFFにしただけで、保護状態を自動的に「一部制限あり」または「保護停止」としてはならない。

Dashboardでは、必要に応じて「🟢 保護中｜カスタム設定」のように二つの軸を同時表示できる。単一の「完全保護」や総合スコアを推測表示してはならず、表示対象となる基盤・ゲーム・セッションの範囲を明示する。

### 3.4.1 Security Foundation と Runtime Protection の表示境界
「Security Foundationが常時有効」という表現は、GST未起動中もFirewallやゲーム監視が継続するという意味ではない。ユーザー向け説明では、Recovery Host、Recovery Journal、Secure Storage、Integrity Verification等の非無効化・常時保持される安全基盤と、GST実行中に提供されるFirewall・ゲーム監視等のRuntime Protectionを分離して示す。OS Auto-startは既定OFFのまま維持し、GST未起動時に提供されないRuntime Protectionを「常時保護」と表現しない。

---

## 3.5 Smart Do Not Disturb と Critical Notification
通常のToast通知はゲーム中のDNDで抑制できる。一方、**保護停止、重大な脅威検知、復旧失敗、重大なユーザー確認要求**はCritical Security/Data Protection Notificationとして扱い、DND中も完全抑制しない。ゲームのフォーカスを奪わない最小表示と未確認状態の永続化を行い、判定不能時もCritical通知まで通常Toastと同じ経路で一律抑制しない。

# 4. 統合検索 ＆ 内蔵マニュアル (Local First Knowledge)

アプリ右上に **統合検索バー（Global Search）** を配置する。検索時には「設定へのショートカット」と「内蔵マニュアル（Markdown）の該当項目」を同時にサジェストし、外部ブラウザを開かせない（Local First）。

## 5.1 AI 8大ユースケース UI
AI 支援機能は、以下の 8 大ユースケースを直感的に呼び出せる専用 UI ボタン・モーダルを提供する：
1. **未署名 MOD レントゲン診断:** PE インポート解析・ZoneId 解析結果を平易に要約説明。
2. **クラッシュレポート即時原因診断:** WER ログや例外ダンプのスタックトレースから推定原因を即時提示。
3. **設定画面 AI コンシェルジュ:** ユーザーの目的に応じた最適プロファイルや設定項目の対話型案内。
4. **コミュニティ脅威 OSINT 調査:** 外部コミュニティで報告された悪性 MOD や既知の不審ハッシュ情報を調査。
5. **マルチプレイ接続トラブルシュート:** 接続障害時の FW ポート・NAT 状況診断と解決策の提示。
6. **セーブ肥大化・異常診断:** 世代間サイズ急増・シャノンエントロピー急変の要因分析。
7. **週間セキュリティ要約:** 直近 7 日間の防御イベント・ブロック履歴のダイジェスト提示。
8. **MOD 起動不能・前提不足相談:** 前提 MOD やランタイム欠落の特定と安全な解決手順案内。

## 5.2 AI ガードレール UX (Prompt Preview ＆ 免責 ＆ 微調整)
- **送信前プロンプト確認 (Prompt Preview):** クラウドへ送信されるマスキング済み生テキストをモーダルで事前確認・編集・承認可能とする。
- **編集後の再承認:** Prompt Preview後にユーザーが内容を編集した場合、直前のPrepared RequestとApprovalは失効したことを明示し、編集後の内容を再サニタイズ・再Fingerprint・再承認しない限り送信ボタンを有効化しない。
- **分析限界と免責表示:** 「AI の回答は GST ローカルログのみに基づく推測であり、安全性や動作を保証しません」を常にチャット枠内に明記。
- **推奨 FW ルール適用の安全化:** AI が推奨した Firewall ルールを適用する際は、ワンクリック適用導線を提供しつつも、必ず「自己責任免責ダイアログ」と「ポート・プロトコルの微調整 UI」を経由させる。

## 6.1 クイックリカバリ (Quick Recovery / Undo)

Dashboard上の「クイックリカバリ」は、復旧操作を素早く開始するためのショートカットである。ワンクリックで復元処理そのものを無確認実行してはならず、ワンクリック後に必ず復旧レビュー画面を表示する。

復旧レビューでは少なくとも以下を表示する。

- 何を復旧するか
- 現在の状態から何が変わるか
- 復旧後に期待される状態
- 実データの上書き・変更が発生する場合の注意事項

ユーザーが明示的に確認した後、`Review → Confirm → Execute` の順で実復旧を開始する。実データを変更する復旧について、確認前に実行・予約・暗黙承認を行ってはならない。

**表示例:** `↩ クイックリカバリ` → 復旧レビュー → `復旧を実行` / `キャンセル`

## 7.1 外部ツール連携 UX ＆ OS 自動起動設定
- **外部ファイル圧縮ソフトウェア呼出:** ゲーム本体バックアップ時の誤操作防止のため、「圧縮開始前の詳細設定ダイアログ表示」チェックボックスは **既定 ON** とする。
- **外部セキュリティスキャナ連携:** 定期スキャンは **既定 OFF（オプトイン）** とし、ゲーム実行中は負荷防止のため **絶対延期** とする。
- **OS 自動起動 (Run キー):** GST 本体の Windows ログオン時自動起動は **既定 OFF（オプトイン）** とし、設定画面でユーザーが明示的に ON にした場合のみ登録する。

# 8. Error Display Model (Actionable Errors)
エラー表示は内部エラーコードの羅列を禁止し、解決策を提示する。外部ファイル圧縮ソフトウェア等による圧縮・展開失敗時は安全な標準 ZIP 等へフォールバックし、データ保護を最優先とする。

---

# 9. Accessibility & User Error Prevention
* **Destructive Actions:** 削除、復元上書き、Firewall ルール削除などは「ワンクリック即時実行」を禁止。必ず Review ➔ Confirm ➔ Execute のステップを踏む。
* **Accessibility:** コントラスト比確保、キーボードナビゲーション対応、意味のあるアイコン実装。

## 10.2.1 アンインストール異常時のRecovery UX（）

正常完了だけでなく、アンインストール中断・電源断・クラッシュ・復元失敗などの非正常状態では、GSTは「完全に元に戻った」と表示してはならない。ユーザーには、現在のトランザクション状態と必要な次の行動を提示する。

```text
状態例: 復元が必要 / 復元中 / 復元が完了 / 復元がブロックされています / 復元に失敗しました

[ 詳細な復旧状態を確認 ] [ Recovery Host を起動 ] [ キャンセル ]
```

`GameSecurityTool.Recovery.exe` による復旧は独立したRecovery Hostで行い、Recovery Hostの操作は `Inspect → User Confirm → Recover → Verify` に従う。正常アプリのSQLite/通常設定が利用できない場合でも、Recovery Hostが利用可能な範囲の復旧操作を提示できる。Recovery Host自身の整合性確認に失敗した場合は復旧操作を開始せず、fail-closedで停止する。


警告ダイアログは最前面に表示するが、監視ゲームの入力を永続的に奪う設計にはせず、ユーザーが選択したアクションをApplication Portへ委譲する。再開・終了の結果は監査ログへ記録する。

** Operational State / Manual Terminate Safety:**
- WIPERの保護状態は、実際の監視WatcherとCanaryの成立状況を反映し、必須構成が満たせない場合は **🔴 保護停止** として表示する。監視障害発生時は、残存Watcherによるファイルイベント起点の自動制御を継続しない。
- 「🛑 強制終了」は誤操作防止のため二段階確認とする。**1回目のクリックは確認待ちのみ**、10秒以内の**2回目のクリック**で既存のPID + StartTime検証済みTerminatorを実行する。期限切れ、新しいアラート、再開操作、操作完了時には確認状態を失効させる。
- 設定画面で事前に `BreakerActionType.TerminateProcess` を明示選択した自動ブレーカーは、この手動確認フローとは別の既存契約として扱う。


### 10.9.1 Presentation State Mapping / Stale Session Boundary
- `MainWindowViewModel` がWIPERのPresentation stateを保持し、`WiperBreakerTriggeredEventDto` と `WiperChildProcessControlResultDto` を表示用状態へ投影する。
- background eventは `IDispatcherService` を経由してUI threadへ同期する。View/Code-behindはWIPERのInfrastructure APIを直接呼び出さない。
- Alert action bindingは **OffendingProcessId + OffendingProcessStartTimeUtc** の組とし、`Resume` / `Terminate` は `IWiperDefenseCoordinator` を介してApplicationへ委譲する。
- Applicationは現在の保護セッションとStartTimeが一致しない操作を拒否し、Infrastructureも同じStartTimeを再検証する。
- 旧アラートの非同期操作が完了した時点で新しいアラートが表示中なら、旧操作結果は新しい表示状態を隠蔽・上書きしない。
- ViewModelのDispose時にはイベント購読を解除する。UI層はセキュリティ判断を実装せず、結果DTOの表示状態への変換だけを担当する。
